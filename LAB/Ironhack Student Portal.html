Learning Objectives

  • Structure a production-grade Terraform repository with CI/CD from day one
  • Enforce conventional commit messages with automated linting

Prerequisites

  • Completed Labs M5.01–M5.09

Introduction

Throughout Week 5 you've built individual CI/CD skills — workflows, pipelines, testing, secrets, and optimization. This capstone lab brings them all together into a single production-grade repository that follows the practices real cloud engineering teams use every day. You'll create the kind of repo structure you'd be proud to show in an interview or hand off to a teammate.

Scenario

Your team is starting a new infrastructure project to manage shared resources (an S3 bucket for artifacts and a DynamoDB table for application state). The team lead wants this repo to be the gold standard for how the team does Infrastructure as Code going forward. That means: enforced commit conventions, automated versioning, a full CI gate, a CD pipeline with approval, clear contribution guidelines, and a deployment failure playbook.

Your Task

What you'll build:

  • Terraform configuration for S3 + DynamoDB resources
  • Conventional commit enforcement via commitlint
  • Automated semantic versioning with release-please
  • CI workflow: format, validate, security scan (tfsec), plan
  • CD workflow with a manual approval gate using GitHub environments
  • README with workflow status badges
  • CONTRIBUTING.md with team conventions
  • Deployment failure postmortem template

Success criteria:

  • Terraform code validates and plans successfully
  • Commit lint check rejects non-conventional commits
  • CI workflow runs format, validate, tfsec, and plan
  • CD workflow requires manual approval before apply
  • README displays workflow status badges
  • CONTRIBUTING.md documents conventions
  • Postmortem template included
  • Documentation complete

### Step 8: Create CONTRIBUTING.md

Create `CONTRIBUTING.md`:

```markdown
# Contributing Guide

## Commit Conventions

This repository uses [Conventional Commits](https://www.conventionalcommits.org/). All PR titles **must** follow this format:

type: short description


### Allowed Types

| Type | When to Use | Example |
|------|------------|---------|
| `feat` | New infrastructure resource | `feat: add CloudWatch alarm for DynamoDB` |
| `fix` | Bug fix or misconfiguration | `fix: correct S3 bucket policy permissions` |
| `docs` | Documentation only | `docs: update architecture diagram` |
| `chore` | Maintenance, dependencies | `chore: update Terraform provider to 5.30` |
| `refactor` | Code restructuring, no behavior change | `refactor: extract S3 config into module` |
| `ci` | CI/CD workflow changes | `ci: add tfsec to pull request checks` |
| `test` | Adding or updating tests | `test: add validation for DynamoDB schema` |

## Pull Request Process

1. Create a feature branch from `main`: `git checkout -b feat/your-feature`
2. Make changes and commit with conventional messages
3. Push and open a PR with a conventional title
4. CI pipeline runs automatically — all checks must pass
5. Get at least one approval from a reviewer
6. Squash merge to `main`
7. CD pipeline runs and waits for production approval

## CI Pipeline Checks

Every PR must pass these checks before merge:

- **Terraform Format** — `terraform fmt -check`
- **Terraform Validate** — `terraform validate`
- **Security Scan** — tfsec checks for misconfigurations
- **Terraform Plan** — plan output posted as PR comment

## Deployment

Merges to `main` trigger the CD pipeline:
1. Automatic `terraform plan`
2. **Manual approval required** in the `production` environment
3. `terraform apply` executes after approval

## Security

- Never commit `.tfvars` files with real values
- Use GitHub Secrets for AWS credentials
- All S3 buckets must have encryption and public access blocks
- DynamoDB tables must enable encryption and point-in-time recovery

Key Takeaways

  • Conventional commits make changelogs, versioning, and release automation possible — they're worth the discipline
  • CI gates (format, validate, security scan, plan) catch problems before they reach production
  • Manual approval gates on CD pipelines add a human checkpoint for high-risk changes
  • CONTRIBUTING.md removes guesswork for new team members and enforces shared standards
  • Postmortem templates turn failures into improvements — the best teams write them before they need them
  • Status badges give instant visibility into repository health
